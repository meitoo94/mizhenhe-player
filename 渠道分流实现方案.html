渠道分流实现方案：倒计时 + 视频内容 + VIP 充值

按渠道号在运行时切换业务形态的可运行最小工程 · 服务端 Python 标准库 / 客户端 SwiftUI / 落地页 H5 · 2026-11-25 本地实测通过

需求对齐：不绑定具体视频题材，实现的是「一个由服务端配置驱动的三段式壳」——开屏倒计时视频试看倒计时VIP 套餐与充值。视频地址、倒计时秒数、套餐价格、按钮文案全部是配置项，题材换素材即可。

一句话原理：iOS 不允许像安卓那样按渠道打不同二进制包，所以渠道号必须通过「广告点击侧 → 首次启动侧」的归因链路带进去；App 启动时拿渠道号请求配置服务，服务端决定这台设备跑 normal 还是 paywall，客户端只执行结果。二进制里两套 UI 都编译进去，但没有任何硬编码的渠道判断。

2. 真正的难点：跨安装把渠道号带进 App

从广告点击到首次启动中间隔着 App Store，没有系统级参数透传。iOS 一个 Bundle ID 只有一个二进制，也不存在「渠道包」。工程上只有下面四条路，实际项目一般同时接前三条做优先级兜底。

方案怎么把渠道号带过去覆盖限制与代价
① 剪贴板签名凭据
已实现		 落地页在「去下载」点击手势内调用 clipboard.writeText，写入 https://ch.example.com/t/<urlencoded CHTOK1#click_id|channel|ts|sig>；App 首启读取并验签，服务端按 click_id 反查渠道。读完立刻清空。 任意广告渠道，精度最高（置信度 1.0） iOS 16+ 读 UIPasteboard.string 会弹系统粘贴许可；用 detectPatterns(for:[.probableWebURL]) 静默预探测，只对命中者读取。用户手动复制别的内容会丢失凭据。
② Apple Search Ads 归因
接口位已留		 客户端 AAAttribution.attributionToken()（AdServices，iOS 14.3+），服务端 POST https://api-adservices.apple.com/api/v1/ 换出 campaignId，再映射到内部渠道号。 仅 Apple Search Ads 流量，官方且不可伪造 不覆盖信息流/短视频/联盟广告；需要服务端实现 token 换取与 campaignId → channel 映射表。本工程已留 asa_token 上报位。
③ 设备指纹概率匹配
已实现		 广告侧记录 IP / UA / 机型 / 时区 / 语言 / 屏幕 / 时间戳；App 首启上报同组字段，服务端在近 24h 点击日志里加权打分找最匹配的一条。 剪贴板被清、ASA 不命中时的兜底 有误判风险：同一运营商 NAT 出口下无关用户可能撞车。已加两道硬门槛：非 IP 维度至少命中 2 项 且 总分 ≥ 70，实测把误判从 68 分挡下。
④ Deferred Deep Link
可接入		 AppsFlyer / Adjust Onelink 或自建 Universal Link：点击时存设备指纹，首启通过 SDK 取回延迟深度链接参数（含渠道号）。 全渠道，商业 SDK 精度较高 需要接第三方 SDK（隐私清单、ATT 适配、额外成本），或自建一套等价的指纹服务 —— 也就是方案 ③ 的加强版。
卸载重装仍能保持渠道态：归因结果写 Keychain 而不是 UserDefaults（ios/KeychainStore.swift:53 同时持久化首次安装时间）。同一台设备重装后无需再点广告，配置服务仍能按原渠道判定。

4. 决策引擎：一台设备落在哪个形态，由这些输入共同决定

客户端只上报 channel / idfv / build / country / install_ts 和 IP，所有判断在服务端 resolve() 里完成，逐条短路返回 normal。这也是「同一商店包，不同人打开不一样」的全部原因。

为什么必须「默认 normal」：把付费墙设为「需要所有条件同时成立才开」，而不是「出错就开」，可以让无网、超时、服务端故障、渠道缺失、配置异常这些情况全部自然落到合规态。这既是稳定性设计，也让配置服务的可用性成为唯一开关点。

① 开屏倒计时

全屏品牌页 + N 秒倒计时按钮，倒计时归零或点击「进入」进入试看。秒数、文案全来自配置。

② 视频试看倒计时

AVPlayer 播服务端下发的 video_url，右上常驻会员入口，底部显示剩余秒数与提示小字，归零弹「试看结束」双按钮。

③ VIP 套餐与充值

套餐列表、划线原价、推荐标签、协议文字、支付按钮全部配置化；选中套餐后创建订单并拉起收银台。

④ 回前台解锁

从 H5 收银台返回时查 /v1/vip/status，已支付则切到无倒计时全屏播放页。

签名方式做了一个工程处理：服务端把配置对象序列化成规范化 JSON 字符串，对这段字符串的原始字节做 HMAC-SHA256，响应为 {config: "<json string>", sig: "..."}。客户端直接验字符串字节再反序列化，避免 Python 的 198.0 与 Swift 的 198 这类跨语言浮点/键序序列化差异导致验签失败（server/app.py:279 / ios/RemoteConfig.swift:89）。生产建议升级成「服务端私钥签 Ed25519 + 客户端内置公钥验」，对称密钥存在被从二进制抠出的可能。

6. 支付闭环

整套账号、订单、会员状态都在自建服务端，不依赖 StoreKit：

  1. 客户端选中套餐 → POST /v1/order，服务端按渠道表校验套餐与金额，生成订单号和收银台地址
  2. UIApplication.shared.open 拉起自建订单页，由它 302 到 mclient.alipay.com H5 收银台（录屏里 trade.jxpdf.com → 支付宝就是这一跳）
  3. 支付通道回调 /v1/pay/notify → 订单标记 paid、写入会员有效期
  4. App 从后台回前台 → /v1/vip/status → 切到已解锁形态

8. 工程要点与边界

  • 归因误判是概率方案的固有局限。同出口 IP + 同时区 + 同屏幕的无关用户仍可能撞车。生产应把指纹当作低置信度补充：要么要求 confidence ≥ 0.9，要么只在点击侧与 App 侧都能拿到高精度信号（IDFV 关联、deferred deeplink）时才采信。
  • 缓存策略。客户端按 ttl=600s 缓存配置用于秒开，过期且拉取失败即回落 normal；验签失败会主动清缓存。生产可把 TTL 拉长，但要权衡「关开关后多久全量生效」。
  • 配置签名。当前用对称 HMAC 演示，生产换非对称签名；issued_at 新鲜度校验阻断旧配置重放。
  • 资源不下发在包内。视频 URL、海报、套餐价格全部走配置，包内没有可直接静态比对的付费素材。
  • 开关维度可继续加。目前实现了渠道/国家/版本/IP/安装时长/时间窗/灰度；还可以接设备型号、系统版本、语言、Apple 归因 campaignId、账号白名单等。
  • 服务端要换成生产部署。当前是标准库 ThreadingHTTPServer + 内存状态 + jsonl 落盘，用于验证链路；生产换成带持久库的服务（渠道表、点击日志、订单、会员、去重），全链路 HTTPS。

接到真实项目里要做的六件事

  1. 新建 SwiftUI 工程，把 ios/*.swift 全部拖入；AppEntry.swift:11 的 baseURL 换成自己的 HTTPS 配置域名。
  2. Info.plist 配 NSAppTransportSecurity（本地 http 联调）、IDFA/ATT 视归因方案而定；加 PrivacyInfo.xcprivacy 声明所需 API 与数据收集。
  3. 合规态页面换成你自己的正常业务；付费墙态的 CDN 视频、海报、套餐、协议 URL 移到服务端渠道表。
  4. 把 CHANNELS 从代码常量改成数据库表 + 管理后台，投放时按 campaign 建渠道号，落地页用 /lp?ch= 分发。
  5. 按上一轮结论准备 macOS 构建环境（CI 即可）：编译、签名、上传仍必须在 macOS 上跑，这套分流逻辑本身与构建平台无关。
  6. 订单/会员接真实支付通道并做服务端验签回调；若要走 App 内购买，则把 checkout.method 换成 StoreKit 2 实现，配置结构不用改。
